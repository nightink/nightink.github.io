3.2 Agent Loop：418 行的双循环引擎

Pi 的核心 agent loop 仅约 418 行代码，实现了精巧的双循环架构：

外层循环 (Outer Loop)

负责会话管理、消息路由、扩展生命周期。接收用户输入 → 组装上下文 → 调用模型 → 处理响应。

内层循环 (Inner Loop)

工具执行引擎。模型返回工具调用 → 执行工具 → 将结果注入上下文 → 再次调用模型 → 直到模型不再请求工具。

用户输入 │ ▼ ┌──────────────────────────────────┐ │ Outer Loop │ │ ┌────────────────────────────┐ │ │ │ 1. 组装 System Prompt │ │ │ │ + AGENTS.md │ │ │ │ + Skills 索引 │ │ │ │ + Extension hooks │ │ │ ├────────────────────────────┤ │ │ │ 2. 调用 LLM Provider │◄─┼──┐ │ │ (via @pi/ai) │ │ │ │ ├────────────────────────────┤ │ │ │ │ 3. 解析响应 │ │ │ │ │ - 文本 → 输出给用户 │ │ │ │ │ - 工具调用 → Inner Loop │ │ │ │ └────────────────────────────┘ │ │ │ │ │ │ │ ▼ │ │ │ ┌────────────────────────────┐ │ │ │ │ Inner Loop │ │ │ │ │ │ │ │ │ │ 执行工具 → 结果注入上下文 │──┘ │ │ │ ↓ │ │ │ │ 模型还有工具调用？ │─────┘ │ │ 是 → 继续 否 → 退出 │ └────────────────────────────┘ │ │ │ ▼ │ 4. 3.3 Session Tree：树状会话结构

Pi 的会话不是线性列表，而是一棵树。用户可以：

  • 回退到任意历史消息
  • 从该节点创建分支（如运行代码审查）
  • 将分支发现带回主上下文
  • 在不同分支间自由切换
🌳 实际场景：主分支做功能开发 → 分支 A 做 code review → 分支 B 跑测试 → 将发现合并回主分支。这种结构让 Pi 在复杂项目中保持上下文清晰。

⚡ 4. Codemode：工具组合的沙盒革命

Codemode 是 Pi 1.0 引入的核心创新，解决了 AI coding agent 领域最棘手的问题之一：多步工具调用的 token 爆炸和网络往返开销。

4.1 问题背景

传统模式：模型需要读取 10 个文件 → 发出 10 次 read 工具调用 → 每次调用都经过完整的 model→harness→tool→harness→model 循环 → 10 轮对话消耗大量 token。

Codemode 模式：模型写一段 JavaScript 脚本 → 在 QuickJS 沙箱中执行 → 脚本内部并行调用 10 次 read → 只返回过滤后的最终结果 → 1 轮对话完成。

4.2 技术实现

┌─────────────────────────────────────────────────┐ │ Codemode 架构 │ ├─────────────────────────────────────────────────┤ │ │ │ Model 输出 JavaScript 源码 │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────┐ │ │ │ QuickJS Sandbox │ │ │ │ ┌─────────────────────────────┐ │ │ │ │ │ • 无 Node API │ │ │ │ │ │ • 无文件系统访问 │ │ │ │ │ │ • 无网络访问 │ │ │ │ │ │ • 无定时器 │ │ │ │ │ │ • 仅通过 tools 和 models │ │ │ │ │ │ 与外界交互 │ │ │ │ │ └─────────────────────────────┘ │ │ │ │ │ │ │ │ 可用能力: │ │ │ │ • await tools.read({path: "..."}) │ │ │ │ • await tools.bash({cmd: "..."}) │ │ │ │ • await models.classify({...}) │ │ │ │ • await models.generateImages() │ │ │ │ • Promise.all() 并行执行 │ │ │ │ • top-level await + return │ │ │ └─────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ 只有脚本输出返回模型上下文 │ │ (文本 + 图片，结构化结果) │ └─────────────────────────────────────────────────┘

4.3 v1.4.0 Codemode 增强

🖼️ 图像分类器支持

models.classify() 新增图像输入，支持 TypeSafe Jev、Cloudflare Clef 模型，覆盖 typesafe、cloudflare-workers-ai、OpenRouter 三个提供商。

⏳ Worker 队列机制

并行脚本和进程内子代理不再因 worker 繁忙而立即失败。新脚本排队等待（最多 60 秒），PI_CODEMODE_MAX_WORKERS 环境变量可提升默认 2 个 worker 上限。

4.4 Codemode 的三大优势

优势说明量化影响
Token 节省 中间结果不进入上下文，只有最终输出 10 次 read → 1 次调用，减少 ~90% 中间 token
延迟降低 并行执行替代串行往返 N 次串行 → 1 次并行，延迟从 N×RTT 降至 ~1×RTT
组合能力 JavaScript 原生控制流 + 非 LLM 模型调用 分类器、视觉模型可直接在脚本中调用
🔑 关键设计决策：Pi 将沙箱放在 harness 层而非 MCP server 层。一个沙箱，所有 MCP 工具可用，跨供应商组合无缝工作。这解决了早期 MCP 实现中 "每个 server 自带沙箱、互相无法调用" 的组合性问题。

🔒 5. Pi Durable：持久化 Agent 基础设施

Pi Durable 是随 Pi 1.0 发布的实验性包，为构建永不宕机的 Agent 应用提供基础设施。它不是新的 coding agent CLI，而是一个构建块。

5.1 核心机制

┌─────────────────────────────────────────────────────┐ │ Pi Durable 架构 │ ├─────────────────────────────────────────────────────┤ │ │ │ 每次模型调用 & 工具调用 = 一个 Task │ │ │ │ │ ▼ │ │ ┌──────────────────────────────────────┐ │ │ │ Checkpoint 机制 │ │ │ │ │ │ │ │ Task 开始 → 记录到 Storage │ │ │ │ 工具执行 → 标记 replay-safe? │ │ │ │ 结果提交 → 持久化 Entry │ │ │ │ Task 完成 → 标记 committed │ │ │ └──────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌──────────────────────────────────────┐ │ │ │ Storage 选项 │ │ │ │ │ │ │ │ 📦 SQLite (默认，本地持久化) │ │ │ │ 📄 JSONL (文件日志，可审计) │ │ │ │ 💾 Memory (测试用，不持久化) │ │ │ └──────────────────────────────────────┘ │ │ │ │ 崩溃恢复路径: │ │ 进程死亡 → 新进程打开同一 DB → 从最后 checkpoint 恢复 │ │ • 已完成的工具调用 → 跳过 │ │ • replay-safe 工具 → 自动重放 │ │ • 非 replay-safe 工具 → 通知模型被中断 │ │ • 被截断的模型请求 → 重发（保留部分结果） │ └─────────────────────────────────────────────────────┘

5.2 Cloudflare 集成

v1.4.0 同期，Cloudflare Agents SDK v0.30.0 发布了 PiHarness 支持：

  • PiHarness：在 Durable Object 的 SQLite 中运行 Pi，自动唤醒处理待完成任务
  • 存储错误恢复：存储错误后自动重新打开 Pi，而非每次调用都失败
  • 唤醒任务重试：失败步骤使用退避策略重试
  • 模型流重试：截断或空闲的模型流报告为瞬态错误，Pi 自动重试该轮
⚠️ 注意事项：Pi Durable API 仍为实验性。默认 SQLite 存储不保证断电持久性。工具作者需要显式标记工具为 replay-safe 才能启用自动恢复。生产使用需直接测试崩溃恢复行为。

🔧 7. v1.4.0 版本变更详解

发布于 2026 年 10 月 21 日，包含 5 项新特性、7 项变更、20+ 项 bug 修复。

7.1 新特性

NEW

图像分类器输入

models.classify() 接受图像输入，支持 TypeSafe Jev 和 Cloudflare Clef 模型。新增 Clef Omni 和 Jev 1.14 支持。

NEW

Models Configuration 参考

从 models.json schema 自动生成的完整配置参考文档，覆盖所有 provider、model、override 和 compat 字段。

NEW

无固定输出上限的摘要

Compaction 和分支摘要改用模型输出限制而非固定 token 上限，长推理不再导致摘要失败。

NEW

Codemode Worker 队列

并行脚本排队等待空闲 worker（最多 60s），PI_CODEMODE_MAX_WORKERS 可提升 worker 数量。

NEW

Rex 终端支持

支持 Rex 终端的 OSC 8 超链接、真彩色和内联图像。

🧠 11. 设计哲学：极简主义的胜利

11.1 核心信条

"Frontier models are so heavily trained on agentic coding that long harness prompts add little."

— Mario Zechner

当前沿模型已经在海量 agent 编码数据上训练后，冗长的 harness 提示几乎不增加价值。Pi 的系统提示 + 工具定义总共不到 1000 tokens。

11.2 刻意省略清单

省略的功能理由替代方案

11.3 "Grow the Harness" 理论

Pi 团队推崇的理念：重复性的控制应该沉入外围代码（extensions），而非让 prompts 无限膨胀。

传统 Harness 思路: 新功能 → 加到 system prompt → prompt 越来越大 → token 成本上升 → 模型注意力稀释 Pi 的思路 (Grow the Harness): 新功能 → 写成 extension → 按需加载 → prompt 保持精简 → 只在需要时占用 context → 可热重载、可组合、可测试
📊 实证支持：Databricks 基准测试证明，这种极简策略在真实百万行代码库上有效。Pi 每轮发送约 3 倍少的 context，成本降低 2 倍以上，质量保持不变。

⚠️ 12. 风险与局限性

✅ 优势

  • Token 效率业界领先
  • 扩展系统极其灵活
  • 模型无关，15+ 提供商
  • MIT 许可，社区活跃
  • Codemode 创新解决 token 爆炸
  • Durable 支持 always-on 场景
  • 多种集成模式 (CLI/RPC/SDK)
  • Earendil 资金充足，方向清晰

❌ 风险

  • 无内置安全护栏，生产环境风险
  • Pi Durable API 仍为实验性
  • 学习曲线陡峭（类 Neovim）
  • 未来增值功能可能 Fair Source 许可
  • Agent 生成的低质量 PR 影响维护效率
  • SQLite 默认存储不保证断电持久
  • Bedrock 上 prompt caching 可能不生效
  • 团队规模小，关键人风险

🎯 13. 结论与展望

核心判断

Pi Coding Agent v1.4.0 代表了 AI coding agent 领域一股重要的反潮流力量：在所有人都在往 harness 里塞更多功能时，Pi 证明了极简 + 可扩展的路线不仅可行，而且在成本和效率上有结构性优势。

三个关键洞察

1. Harness 是新的成本杠杆

Databricks 实证表明，harness 选择对成本的影响超过模型选择。Pi 的 context discipline 使其在相同质量下成本降低 2 倍以上。这意味着工程团队的 harness 选型决策比模型选型更影响底线。

2. Codemode 是 MCP 的正确打开方式

Pi 没有简单地把 MCP 工具 dump 进 context，而是通过 Codemode 沙箱让模型在代码中组合工具。这解决了 MCP 的组合性问题，同时保持了 token 效率。沙箱在 harness 层而非 server 层是关键设计决策。

3. 极简不是缺少功能，而是架构选择

Pi 的 "缺少" 功能（sub-agents、plan mode、权限系统）是刻意为之。每个省略都降低了 prompt 开销，同时通过扩展系统保留了添加能力。这是 Neovim 哲学在 AI agent 领域的复现。

展望

  • Pi Durable 成熟化：从实验性到生产级，SQLite 持久性保证、KV cache 恢复等
  • Fair Source 增值层：Earendil 的商业化路径，核心保持 MIT
  • Cloudflare 深度集成：PiHarness + Durable Object 成为 always-on agent 的标准部署模式
  • 社区 fork 分化：Oh My Pi (全功能) vs Pi (极简) 的路线之争将持续
  • 企业采用：需要补充安全护栏层才能进入受监管环境
